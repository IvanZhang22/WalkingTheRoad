# 行小道 v2.2.0：多模态统一入口整合决策

## 一、已经核验的输入

马仲琪交付的 `8.3行小道-音频MVP-v9` 已在隔离环境运行：37/37 自动测试通过。已具备的可复用能力包括：

- 清小搭 URL 形式的 `input_audio`、`file` content part 解析；
- 下载大小限制、私网/元数据地址拒绝、临时文件清理；
- TXT、DOCX、PDF 文字层解析，以及 OCR 分支；
- Deepgram ASR Provider、时间戳片段、置信度路由；
- 多模态证据的字符、时间戳和 bbox 安全约束；
- 低置信、模糊或跨片段证据只进人工复核，不能自动进入正式主题分析。

## 二、不能直接合并的部分

v9 自带 `api/chat_completions.py`，且纯文本请求会返回 501。这与主工程 v2.0.0 的 `POST /v1/chat/completions` 冲突。v2.2.0 的硬规则是：**对外只保留主工程的一个聊天端点**，v9 只作为内部“多模态材料接入层”。

不复制 v9 的 Vercel handler、独立环境变量文件、独立 Chat 端点或清小搭工作流导出。保留并适配其下载、解析、Provider、归一化、置信度与证据定位逻辑。

## 三、统一输入/输出契约

v2.2.0 扩展 v2.0.0 的消息 content：

```json
[
  {"type": "text", "text": "请将这段访谈录音作为质性材料分析"},
  {"type": "input_audio", "input_audio": {"url": "https://oss.../voice.mp3", "format": "mp3"}},
  {"type": "file", "file": {"url": "https://oss.../notes.docx", "filename": "观察笔记.docx"}}
]
```

每个附件都归一化为内部 `Material`：材料 ID、来源 URL、文件名、模态、正文、片段定位、置信度、自动可用性、人工复核队列和异常。主聊天端点把可用正文交给 W3，绝不让未核验的低置信转写直接生成正式引文。

## 四、实现顺序

1. 在主仓库建立 `app/multimodal/`，先迁入并重测不依赖账号的 Downloader、请求解析、文本/PDF/DOCX 解析、归一化和置信度模块；
2. 将主端点的 `ChatMessage.content` 扩展为字符串或 content part 数组，维持 v2.0 文本请求兼容；
3. 将多个附件逐个隔离处理；一个附件失败只返回该材料的结构化错误，不丢弃其它材料；
4. 用真实但已获授权的音频测试 Deepgram，配置 `DEEPGRAM_API_KEY`，并确认时间戳与低置信复核队列；
5. 将通过验收的材料交给 W3 证据提取/核验，不再维护 v9 的独立 chat 端点；
6. 加入清小搭 `x_soda.attachments` 文件输出，只给 URL，不给 base64。

## 五、马仲琪需要交付/确认的内容

1. `8.3` 代码中哪些模块是她确认可合并的正式版本，以及其来源/使用权；
2. Deepgram 真实音频样例的脱敏测试说明、预期片段数、失败状态和费用边界；
3. `DEEPGRAM_API_KEY` 的创建、轮换和 Vercel 配置步骤，不提供任何真实 Key；
4. 多模态模块的公开输入输出 JSON 契约与错误码清单；
5. 至少一次从功能分支发起的练习 PR，确保模块可由张一凡在主工程 CI 中复现。

## 六、v2.2.0 退出条件

- 文字、文件 URL、音频 URL 都通过同一个 `/v1/chat/completions`；
- 纯文本不回归，音频/文件不会被当作字符串或 base64 写入日志；
- 真实音频至少一例成功且可按时间戳回看，低置信样例不自动成为正式证据；
- 文件下载、格式、大小、超时、私网 URL 和单附件失败均有自动测试；
- 现有 39 项主工程测试和迁入模块测试同时通过；
- 清小搭端完成一次真实附件试聊后，才对外勾选对应多模态能力。
